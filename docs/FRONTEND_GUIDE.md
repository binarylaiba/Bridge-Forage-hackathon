| **Audience** | Frontend team |

---

## a. Project Context

This project is a product catalog sandbox that demonstrates an **AI-powered documentation pipeline**. The backend is a Node.js/Express CRUD API persisting a list of products (`{ id, title, price }`) to a local JSON file. The frontend team's job is to build a React UI that consumes that API.

**Why docs are auto-generated**

A file watcher (`watcher/watch.js`) monitors `backend/routes/` using chokidar. Whenever a backend route file is saved — including field-name renames — the watcher calls the IBM Bob CLI with a prompt template that instructs Bob to:

1. Read the updated backend source to derive the current Product schema.
2. Overwrite `docs/API.md` with a corrected human-readable reference.
3. Overwrite `docs/openapi.json` with a corrected OpenAPI 3.0 spec.

This means **`docs/API.md` is the single source of truth for field names**. Do not rely on field names you saw previously or that appear in this guide — always confirm against `docs/API.md` before hardcoding anything.

## b. Tech Stack Recommendation

| Concern | Choice |
|---|---|
| Bundler / dev server | [Vite](https://vitejs.dev/) |
| UI library | React 18 (JavaScript, no TypeScript required) |
| HTTP | `fetch` (built-in) — no Axios needed at this scale |
| State management | React `useState` + `useEffect` |

**Scaffold a new project**

```bash
npm create vite@latest frontend -- --template react
cd frontend
npm install
npm run dev   # starts on http://localhost:5173
```

**Vite proxy — eliminate CORS entirely**

Add a `server.proxy` entry in `vite.config.js` so that requests from the browser to `/api/*` are forwarded to the backend. You never touch CORS headers client-side.

```js
// vite.config.js
import { defineConfig } from 'vite'
import react from '@vitejs/plugin-react'

export default defineConfig({
  plugins: [react()],
  server: {
    port: 5173,
    proxy: {
      '/api': {
        target: 'http://localhost:3001',
        changeOrigin: true,
      },
    },
  },
})
```

With this config in place, `fetch('/api/products')` inside the browser resolves to `http://localhost:3001/api/products`. No `Access-Control-Allow-Origin` headers need to be set anywhere in client code.

## d. Current Data Model

The following table reflects the Product schema **at the time this guide was written**. It may be out of date.

| Field | Type | Constraints | Notes |
|---|---|---|---|
| `id` | string (UUID v4) | Read-only, auto-generated | Never send this field in a POST or PUT request body. |
| `title` | string | Required | Display name of the product. |
| `price` | number | Required | Price in dollars. |

> ⚠️ **This field name may be renamed by the AI pipeline — always check [`docs/API.md`](./API.md) for the current contract before hardcoding field names.** If `title` has been renamed (e.g. to `productName`), every reference in your components and API wrapper must be updated to match.

## e. Suggested Component Map

Three components cover the full UI. Keep them in `src/components/`.

### `ProductList`

Renders a table of all products.

- **Props:** `products` (array), `onEdit(product)` (callback), `onDelete(id)` (callback)
- **Columns:** Title · Price · Actions
- **Actions column:** an Edit button (calls `onEdit` with the full product object) and a Delete button (calls `onDelete` with the product `id`)
- Displays a "No products yet." message when the array is empty

### `ProductForm`

Controlled form used for both creating and editing a product.

- **Props:** `initial` (product object or `null` for create), `onSubmit(data)` (callback), `onCancel()` (callback)
- **Inputs:**
  - `title` — `<input type="text" />`, required
  - `price` — `<input type="number" step="0.01" min="0" />`, required
- When `initial` is non-null, pre-populate fields from the passed object (edit mode)
- Submit button label: **"Save"** (edit) / **"Create"** (new)

### `App`

Root component. Owns all state, orchestrates data fetching, and wires `ProductList` and `ProductForm` together.

- Calls `getProducts()` on mount via `useEffect`
- Passes CRUD callbacks down to child components
- Conditionally renders `ProductForm` based on the `formVisible` flag (see §f)

## f. State Management Notes

Local React state is sufficient for this scale. No Redux, Zustand, or Context API is required.

Recommended state shape inside `App`:

```js
const [products, setProducts]           = useState([])         // full list from GET /api/products
const [editingProduct, setEditingProduct] = useState(null)     // null = create mode; object = edit mode
const [formVisible, setFormVisible]     = useState(false)      // controls whether ProductForm is rendered
```

**Typical flow**

| User action | State change |
|---|---|
| Click "New Product" | `setFormVisible(true)`, `setEditingProduct(null)` |
| Click "Edit" on a row | `setFormVisible(true)`, `setEditingProduct(product)` |
| Submit form (create) | call `createProduct`, then `setProducts([...products, newProduct])`, hide form |
| Submit form (edit) | call `updateProduct`, then replace matching item in `products`, hide form |
| Click "Delete" | call `deleteProduct`, then filter the deleted item out of `products` |
| Click "Cancel" | `setFormVisible(false)`, `setEditingProduct(null)` |

Avoid re-fetching the full list after every mutation — update local state optimistically for a snappier UI. If you prefer simpler correctness over performance, re-call `getProducts()` after each mutation instead.

## g. Integration Checklist

Work through this list in order before considering the integration complete.

1. [ ] Backend is running on port 3001 (`cd backend && npm run dev` — no errors in that terminal).
2. [ ] Vite proxy is configured in `vite.config.js` as shown in §b.
3. [ ] `GET /api/products` returns data — confirm in the browser DevTools **Network** tab (status `200`, response is a JSON array).
4. [ ] `POST /api/products` creates a product — after submitting the form, the new product appears in the list (either via optimistic update or re-fetch).
5. [ ] `PUT /api/products/:id` updates a product — edited values are reflected in the list immediately.
6. [ ] `DELETE /api/products/:id` removes a product — the row disappears from the list.
7. [ ] All field names used in components and the API wrapper (`title`, `price`, etc.) match the **Data Model** section of [`docs/API.md`](./API.md) exactly — no spelling differences, no camelCase/snake_case mismatches.
8. [ ] No field name strings are hardcoded in more than one place without being checked against [`docs/API.md`](./API.md). If `docs/API.md` changes, the diff should point you to every location that needs updating.

## h. Breaking-Change Notice

**How the AI pipeline works at runtime**

`watcher/watch.js` uses chokidar to watch every file under `backend/routes/`. The instant any route file is saved, the watcher:

1. Reads `watcher/prompts/update-docs.md` (the Bob prompt template).
2. Injects the changed file path into the template.
3. Shells out to the IBM Bob CLI to execute the prompt.
4. Bob reads the updated backend source, derives the new Product schema, and **overwrites** both `docs/API.md` and `docs/openapi.json`.

**What this means for the frontend team**

If the backend developer renames a field (e.g. `title` → `productName`), the next time they save the route file both doc artifacts are regenerated automatically — usually within seconds. Your code will break silently until you update it.

**Recommended practice**

- **Watch the `docs/` folder in git.** Run `git pull` frequently during active backend development. Any commit that touches `docs/API.md` or `docs/openapi.json` is a signal that field names may have changed.
- Set up a git hook or CI check that fails if `docs/API.md` is updated but the frontend source still references the old field name.
- When you see a doc change, search your entire frontend source for the old field name and replace every occurrence.

> The Bob CLI regenerates docs — it does **not** automatically update your React code. That step is always manual.
